## 1. Контекст и цель

**Проект:** [volgarevmaxim-bit/schools-map-mathex](https://github.com/volgarevmaxim-bit/schools-map-mathex) — статический сайт-карта школ и детских садов Москвы (Leaflet, GitHub Pages). Состав: исследовательские списки (mathex.ru × Forbes, 69 школ), карта точек (`places.json`, 45 объектов с меткой `kind`), редакционный контент (`schools_content.json`), сборочные скрипты.

**Появился downstream-потребитель:** проект openhouse-radar (еженедельный радар дней открытых дверей) берёт из этого репозитория реестр школ и метку `kind`: `green` = сад, `blue` = приём с 1 класса, `red` = остальное. Для мониторинга нужны записи с `kind=blue`.

**Симптом поломки:** при сопоставлении `schools_normalized.csv` (69 строк) с `places.json` (45 объектов) корректный blue-матч находится ровно **один** («Интеграция XXI век»). Реестр радара из 69 школ сжимается до 1. Дата-флоу проекта в текущем виде непригоден как источник для потребителя.

**Цель работ:** единый воспроизводимый дата-флоу — канонический реестр сущностей школ/садов, из которого одной командой генерируются все живые артефакты (карта, CSV, контент), с валидаторами, документацией и пригодностью в качестве upstream для openhouse-radar.

**Важно:** причина поломки ниже — *гипотеза* (§3, S1). Диагностика — предмет Фазы А. Не принимать на веру, подтвердить или опровергнуть данными.

## 2. Границы и порядок работ

- **Фаза А — аудит: строго read-only.** Ничего не менять в репозитории; результат — документ `AUDIT.md` в корне (или `docs/`, по вкусу). **Gate 1: ревью AUDIT.md владельцем.** Без его «ок» Фаза Б не стартует.
- **Фаза Б — рефакторинг:** только после Gate 1, в feature-ветке; в `main` — через ревью владельца.
- **Не трогать без явного разрешения владельца:** `app.js`, `index.html`, ветку `gh-pages`, процесс публикации (по README публикация в `gh-pages` ручная). Рефакторинг данных не должен менять поведение живого сайта.
- Радар (потребитель) на время работ в паркинге — дедлайна нет.

## 4. Фаза А — аудит (read-only) → `AUDIT.md`

**А1. Lineage-карта всех файлов репозитория (~20):** для каждого — производитель (кто/что генерирует), потребители, статус (живой / зомби / источник), дата последнего осмысленного изменения. Таблица.

**А2. Полный match-отчёт CSV↔places.json по всем 69 строкам** → `match_report.csv`, машиночитаемый (важно: этот отчёт станет входом Этапа 1 радара, см. §6). Колонки:
`csv_id, csv_name, csv_address, place_id, place_name, place_kind, name_score, addr_score, verdict (match / unsure / no_match), comment`.

**А3. Анализ дубликатов и модели сущностей:** где живёт `kind` (точка vs сущность), как схлопнуть точки одной школы (S5), что при этом происходит с метками.

**А4. Ревизия семантики текущих 45 меток `kind`:** что реально означает blue в каждом из 3 случаев; сверка с GREEN/BLUE-хардкодами `build_data.py` (S8) — где расхождения и какая семантика правильная. Выписать все несоответствия списком с evidence.

**А5. Реестр дефектов** с severity (critical / major / minor) и рекомендациями по каждому. Каждый дефект — с доказательством (файл:строка, данные).

**Формат:** `AUDIT.md`, таблицы, без воды. Плюс приложения-данные (`match_report.csv`, при необходимости дампы промежуточных расчётов).

## 5. Фаза Б — рефакторинг

**Б1. Канонический реестр сущностей** `entities.json` (или иное имя по вкусу владельца), схема:
```json
{
  "id": "школа-1535",
  "name": "Школа №1535",
  "name_normalized": "...",
  "address_normalized": "...",
  "kind": "blue",
  "kind_source": "manual review 2026-09-30 | research list | ...",
  "points": [{"place_id": "...", "name": "...", "address": "...", "lat": 0, "lon": 0}],
  "source": "mathex | forbes | both",
  "notes": ""
}
```
`kind` живёт на сущности; точки наследуют. Все сущности из обеих вселенных (CSV 69 + карта 45) должны найти место: либо сущность, либо осознанное исключение с причиной.

**Б2. Backfill меток `kind`:** правила вывода из доступных данных + **review-очередь владельцу** (сомнительные — пачкой одним списком, не по одной). Цель: 0 сущностей без `kind`, 0 без `kind_source`.

**Б3. `build_all.py`:** генерация всех живых артефактов (`places.json`, `schools_normalized.csv`, при необходимости `schools_content.json`-скелет) из канона. Критерий идемпотентности: повторный запуск = **0 diff**.

**Б4. `validate.py`:** схема (JSON Schema или эквивалент), уникальность id, покрытие kind и kind_source, связи точек↔сущностей (каждая точка принадлежит ровно одной сущности), отсутствие дублей имён/адресов сверх ожидаемых. Опционально — GitHub Action на push (Q6).

**Б5. Документация и чистка:** один актуальный handoff; README отражает реальный дата-флоу; судьба зомби-артефактов (S6) и двух handoff'ов — по решению владельца (Q4); зафиксированные зоны ответственности скриптов.

## 6. Контракт с downstream (openhouse-radar)

Радар после рефакторинга берёт из этого репозитория реестр сущностей с полями `id, name, address, kind, kind_source` — совместимо со схемой `schools_filtered.json` из ТЗ радара (п.7 его ТЗ). Требования:

1. **Полнота:** каноническая вселенная покрывает все 69 школ CSV (Q1) — радару нужна полнота списка, а не только 45 точек карты.
2. **Приёмочный метрик:** матчинг по имени+адресу (алгоритм Этапа 1 радара: нормализация + fuzzy + review) находит **≥90% канонических сущностей с `kind=blue`** без ручного ковыряния.
3. `match_report.csv` из Фазы А — машиночитаемый, пригодный для программной обработки радаром.
4. После рефакторинга радар обновит свой снапшот `data/raw/` и SHA в `UPSTREAM.md` — менять API данных без обновления снапшота нельзя.

## 8. Критерии приёмки (измеримые)

1. `AUDIT.md` пройден ревью владельца (Gate 1).
2. Канонический реестр: 0 сущностей без `kind`, 0 без `kind_source`, 0 дублей; `validate.py` зелёный.
3. `build_all.py`: повторный запуск — 0 diff.
4. Каждый живой артефакт имеет ровно один источник (канон) и одного производителя.
5. Контракт радара (§6): матчинг имени+адреса находит ≥90% канонических blue; снапшот радара обновлён.
6. Документация: один handoff, README соответствует реальности, зоны ответственности скриптов описаны.
