# План реализации: радар дней открытых дверей школ Москвы (openhouse-radar)

## 1. Цель и критерии готовности v1

**Цель.** Еженедельно автоматически формировать и отправлять в Telegram Saved Messages сводку по заданному реестру школ Москвы: структурированные анонсы дней открытых дверей (дата, адрес, регистрация, ссылка), заголовки прочих сообщений со ссылками, и явный heartbeat при отсутствии событий за неделю. Источник — Telegram-каналы школ (Telethon), классификация — DeepSeek V4.1 Flash (zero-shot), оркестрация — GitHub Actions (два cron).

**Формат еженедельной сводки (пример из ТЗ):**

> За прошедшую неделю сообщений о планируемых днях открытых дверей в анализируемых школах не было.
> Прочие сообщения: Школа 1537: ...
> (ссылки)

При наличии анонсов — перед блоком прочих сообщений идёт структурированный блок: по каждому событию — школа, дата, адрес, отметка регистрации и ссылка на исходное сообщение.

**Критерии готовности v1 (приёмка):**

| # | Критерий | Способ проверки |
|---|----------|-----------------|
| 1 | Реестр blue-only школ собран, исключения исключены, несопоставленные вынесены в backlog v2 | `data/schools_filtered.json` существует, в нём только blue |
| 2 | Для каждой школы реестра найден Telegram-канал (high-confidence или подтверждён владельцем) | `data/schools_channels.json` — все записи с `match_confidence` |
| 3 | Ежедневный job запускается по cron, читает новые сообщения, классифицирует, сохраняет state | Actions Artifact после первого запуска |
| 4 | Недельный job собирает артефакты за 7 дней, обобщает LLM в человекочитаемую сводку | Сообщение в Saved Messages |
| 5 | При пустой неделе — heartbeat c явным текстом «не было» | Факт отправки |
| 6 | Секретный аккаунт (alter-ego) залогинен, StringSession в GitHub Secrets | Проверка `scripts/login_session.py` |
| 7 | Кириллица в сообщениях не покорёжена (Telethon + DeepSeek) | Визуальная проверка сводки |

### Фаза 2. Сопоставление школа → Telegram-канал

**Задачи:**

2.1. Определить Telegram API credentials:
   - Получить `api_id` и `api_hash` на https://my.telegram.org/apps.
   - Сохранить в `.env` (локально) и в GitHub Secrets (`TG_API_ID`, `TG_API_HASH`).

2.2. Владелец выполняет интерактивный вход для генерации StringSession:
   - **Скрипт:** `scripts/login_session.py` (Telethon `TelegramClient` с `session='string'`).
   - Ввод кода подтверждения — **только человек**.
   - Вывод: `TG_SESSION_STRING` — строка для GitHub Secrets.
   - **Команда:** `python scripts/login_session.py`

2.3. Для каждой школы из `schools_filtered.json` (included=true) найти Telegram-канал:
   - **Критерии уверенности (ТЗ п.5):**
     - *Идентифицирующий признак:* числовой номер школы в username/названии/описании канала.
     - Если номера нет → минимум 2 ключевых слова из названия школы.
     - *Подтверждающий признак (хотя бы один):* слово «официальный» в описании, или контекст Москвы в ленте.
     - *Правило:* идентифицирующий + хотя бы один подтверждающий → high (agent confirms). Иначе → на подтверждение владельцу.
   - **Инструмент:** Telethon `contacts.SearchRequest` (глобальный поиск).
   - **Fallback:** если Telethon не даёт результат → владелец передаёт залогиненную веб-сессию суб-агенту для ручного поиска (ТЗ п.5).
   - **Выходной файл:** `data/schools_channels.json` (схема: `{"school_id","name","tg_username","match_confidence","match_reason"}`).

**Ключевые команды:**

```bash
PYTHONPATH=src python -m radar.stage02_match_channels
# -> Читает data/schools_filtered.json
# -> Использует Telethon для поиска
# -> Пишет data/schools_channels.json
```

**Питфоллы фазы 2:**

| # | Питфолл | Решение |
|---|---------|---------|
| 1 | Telethon может вернуть много мусора | Фильтровать по типу (канал, не пользователь) и по языку/локации |
| 2 | Канал без username (private supergroup) | В `message_link` использовать `https://t.me/c/{chat_id}/{message_id}` — chat_id берётся из `entities` |
| 3 | FloodWaitError при массовом поиске | Добавить паузу ~1 с между запросами, backoff при ошибке |
| 4 | Канал переименовался или удалён | При запуске джоба проверять доступность; если 403/недоступен — log warning, notify |

**Gate (приёмка фазы 2):** владелец подтверждает `data/schools_channels.json` — все каналы верные ✅

### Фаза 4. Upstream + state (ежедневное чтение)

**Задачи:**

4.1. Реализовать модуль `src/radar/reader.py`:
   - Telethon `iter_messages(channel, min_id=last_seen_id)`.
   - Для каналов без username: извлекать `chat_id` из `entity`.
   - Пауза ~0.7 с между каналами (дефолт №8).
   - FloodWaitError → корректный backoff.
   - **Схема хранения state:**
     ```json
     {
       "schools_channels": {"<school_id>": {"last_seen_id": 123, "tg_username": "..."}},
       "last_updated": "2026-09-25T17:00:00Z"
     }
     ```
   - По умолчанию: первый запуск → `last_seen_id` = текущий максимум сообщений канала (дефолт №3).

4.2. GitHub Actions workflow: `.github/workflows/daily_read.yml`
   - Trigger: cron `0 17 * * *` (дефолт №2; 20:00 МСК).
   - Шаги:
     1. Checkout репозитория.
     2. Установка Python + зависимостей (`pip install -r requirements.txt`).
     3. Загрузка state из Artifact (по фиксированному имени `radar-state.json`).
     4. Запуск `PYTHONPATH=src python -m radar.daily`.
     5. Загрузка state обратно в Artifact (retention 90 дней, дефолт №1).
     6. Загрузка raw-сообщений в Artifact `daily-{date}.json`.

4.3. State — GitHub Actions Artifacts (по умолчанию; меняется, если владелец ответит иначе):
   - **Причина:** Actions Cache вытесняется через ~7 дней без обращений → риск потери `last_seen_id`.
   - Retention: 90 дней.
   - Ежедневный job кладёт новый артефакт `daily-{date}.json` с классификациями.
   - **Критично:** недельный job **читает** дневные артефакты (7 штук) и **чистит** их после обработки.

**Создаваемые файлы:**

| Файл | Назначение |
|------|-----------|
| `src/radar/reader.py` | Telethon-чтение + backoff |
| `src/radar/state.py` | Загрузка/сохранение state (Artifacts) |
| `src/radar/daily.py` | CLI entry point: читает → классифицирует → сохраняет |
| `.github/workflows/daily_read.yml` | Cron daily |
| `requirements.txt` | Зависимости (telethon, httpx, pydantic) |

**Gate (приёмка фазы 4):** после первого запуска daily workflow в Actions Artifacts появляются `radar-state.json` и `daily-{date}.json` с корректными сообщениями ✅

## 5. Общие риски проекта

| # | Риск | Влияние | Смягчение |
|---|------|---------|-----------|
| 1 | **Telegram-сессия на GitHub-раннерах.** Раннеры меняют IP при каждом запуске. Telegram может заподозрить подозрительную активность и потребовать перелогин / наложить FloodWait. | Остановка сбора данных на часы/дни | Использовать alter-ego аккаунт (не основной); мониторить ошибки сессии; при сбое — автоматическое уведомление владельцу для ручного перелогина |
| 2 | **Потеря state.** Actions Artifacts живут 90 дней, но при удалении артефакта (вручную или политикой) last_seen_id теряется. | Повторная обработка сообщений → дубли в сводке | Дубли дедуплицируются по `message_link`; при потере state — инициализация последним известным максимумом (но риск дублей на один день) |
| 3 | **Дубли из-за повторных анонсов.** Школа может анонсировать одно событие несколько раз. | Дубли в классификации | Дедупликация по `message_link` (первичный ключ); при одинаковом `event_date` + `school_id` в недельной сводке — группировка |
| 4 | **Лимит 4096 символов.** Сводка может превысить лимит Telegram-сообщения. | Сообщение не отправится | Разбивка на части (дефолт №7); первая часть — блок open_house, вторая — блок прочих сообщений |
| 5 | **Каналы без username.** Нет публичного `t.me/username`. | Нельзя сформировать `message_link` | Использовать `https://t.me/c/{chat_id}/{message_id}` (дефолт №6); `chat_id` извлекать из `entity` при первом чтении |
| 6 | **Шумные каналы.** Некоторые каналы публикуют десятки сообщений в день (объявления, поздравления, погода). | Затраты на классификацию (каждый токен платный) | Промпт на этапе классификации должен компактно summarise «прочие»; при сильном шуме — добавить фильтр по длине (сообщения <50 символов пропускать) |
| 7 | **FloodWaitError от Telegram.** Массовое чтение каналов может вызвать временную блокировку. | Задержка на 1–60 мин | Корректный backoff (дефолт №8); между каналами пауза ~0.7 с; при FloodWait — ждать указанное время и retry |
| 8 | **Смена схемы данных upstream.** schools-map-mathex может изменить формат CSV или добавить колонки. | Поломка Фазы 1 | Снапшот зафиксирован коммитом; обновление — только по решению владельца |
